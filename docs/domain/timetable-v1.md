# Timetable V1 — configuration, manual drafts and publication

Phase 1 configures requirements; Phase 2 creates recurring weekly drafts. Phase 3 publishes immutable weekly schedules and provides authorized Teacher/Parent reads. Drafts remain School Admin only.
This follows ADR-001/004/007/009/010/017 and the existing Academic Structure contracts.

## Scope and precedence

- A teaching-week configuration belongs to an existing School and Academic Year.
- A Level override replaces a Stage override, which replaces the School default. An override replaces the complete week, including working days; slot indexes are not shared between scopes.
- ISO weekdays are 1 (Monday) through 7 (Sunday). Each working day has 1–24 ordered, non-overlapping local-time intervals, including at least one teaching interval. Gaps and breaks are allowed. Overnight intervals are excluded from V1.
- Times are School wall-clock times, not UTC instants. Existing School timezone and school-specific calendar calculations remain authoritative. Phase 2 compares clock intervals only when their recurring date ranges contain the same actual weekday; matching slot indexes cannot establish availability.
- Configuration and Class/Subject load changes append immutable application revisions with actor and timestamp. Restoring inheritance appends a disabled override. The default cannot be disabled. Future timetable versions must reference exact revisions rather than resolve current settings retroactively.
- PLANNED and ACTIVE years are editable; CLOSED and ARCHIVED years remain readable. Existing Academic Periods are not duplicated. Period/date-specific recurring weeks belong to Phase 2 and must reference a Period in the same existing year.

## Rooms and teaching requirements

- Rooms/labs belong to the School, have a unique trimmed name, and can be renamed or deactivated with revision checks. They are never deleted by this API. Room edits emit atomic audit events; future published versions must snapshot room presentation rather than infer old names from current data.
- A requirement specifies positive lessons/week (1–60), minutes/lesson (5–240), and an optional room preference for one Class/Subject. Multiple teachers are supported as separate existing candidate assignments; Phase 1 chooses one assignment for the requirement. It does not introduce co-teaching or split loads.
- Enabled requirements require an active Class, active subject in that Class's exact curriculum version, and an active Teacher Assignment matching School/Class/Subject/Academic Year, with an active Teacher and dates overlapping the year. The curriculum version is recorded on each revision.
- TeacherAssignment remains the only teacher authorization source. Requirements grant no permissions. Phase 2 must revalidate assignment dates, lifecycle, curriculum and room availability for every actual lesson; ending an assignment does not rewrite historical requirements. A requirement may be retired after its assignment ends.
- Room preference is optional and is not a reservation. Phase 1 does not assert schedulability, capacity or conflict freedom. Phase 2 must compare actual start/end intervals, including across different Stage/Level templates, for Teachers, Classes and rooms.

## Write and recovery boundary

- Only verified ACTIVE School Admins in an ACTIVE School can read/manage this administration surface. Platform-only administrators, Teachers and Parents have no Phase 1 settings access.
- Every write rechecks authority while holding School, User and membership locks, with academic/lifecycle rows locked where applicable. School-local serialization plus expected revisions prevents concurrent lost updates. Identical repeated revision updates return the existing revision; stale differing saves fail with a conflict. Duplicate room creation fails rather than creating a second room. Clients do not automatically retry ambiguous writes.
- Composite foreign keys enforce School and Class/year/subject/assignment consistency. Private RLS tables have no public Auth/Data API grants. Cookie-authenticated writes require an exact same Origin. All API responses, including errors, are private/no-store.
- Migration `0027_timetable-foundation` appends to the unchanged `0000`–`0026` chain. It creates three tables and adds one unique Teacher Assignment reference key, with no backfill/default changes to existing academic entities.
- Phase 1 recovery inventory is 54 application + 2 Auth tables; Phase 2 extends this to 56 + 2. Full-row fingerprints and FK-derived restore ordering include all new tables. Historical 0022, Finance-generation and 0027 bundles retain their original inventories and require their matching source/migration chain for restore.

## UI and next phase

`/timetable` provides teaching-week inheritance, room management, Class/Subject requirements, weekly drafts and published Class/Teacher views for School Admins. Teachers get My Timetable; Parents get My Children's Timetables. All use EN/FR/AR, existing controls and unprefixed routes.

## Phase 2 — manual recurring-week drafts

- An ACTIVE School Admin selects an existing Academic Year, Academic Period and Class. The Period must belong to that Year and lie within its dates. PLANNED/ACTIVE years, non-CLOSED Periods and ACTIVE Classes are editable; other valid contexts remain readable.
- A complete draft revision snapshots Period dates, curriculum version and an exact teaching-week configuration revision. New drafts use Level > Stage > School precedence. Later configuration changes require explicit adoption; existing lesson times never silently move. Changed Period dates/curriculum are flagged and stale saves are rejected until reviewed.
- Each lesson occupies one configured teaching interval on an ISO weekday. Breaks and overnight times cannot be lessons. Click/tap editing can change the interval, Subject, existing Teacher Assignment and optional active same-School room. A stable logical lesson key survives moves; removing a lesson appends a new complete revision, preserving previous rows.
- Only ACTIVE Class/Subject/Year assignments with an ACTIVE Teacher and active curriculum Subject are eligible. Assignment dates must cover the first through last actual occurrence of the lesson weekday in the selected Period. Ending an assignment does not erase history; the next save must resolve invalid lessons.
- Class, Teacher and room conflicts use half-open clock intervals and overlapping recurrence dates containing the same weekday. Adjacent intervals are allowed. Checks span the latest drafts of other Classes, Periods and Years in the same School, including different Level schedules. Old revisions do not reserve resources. Incomplete/excess load counts, total minutes and per-lesson duration differences are visible warnings rather than hard conflicts.
- Saves take the shared School write lock and recheck actor/lifecycle and academic references inside the transaction. Expected revisions reject stale writes. A School-scoped request key and canonical payload hash make identical retries safe and reject changed-payload reuse. The client never automatically retries ambiguous writes. Local unsaved edits disable context changes; explicit reload/discard remains available.
- `GET/PUT /api/v1/timetable/draft` is School Admin only, same-Origin for writes and private/no-store for all results. Teachers, Parents and platform-only administrators cannot see unpublished drafts. No publication, substitutions, availability engine or automatic scheduling is introduced.
- Forward migration `0028_timetable-weekly-drafts` creates private RLS `timetable_drafts` and `timetable_lessons` with composite School/context foreign keys and adds the configuration reference key. Existing migrations/snapshots through 0027 remain unchanged. The journal appends index 28 (29 migrations total).
- Current recovery covers 56 application + 2 Auth tables, including nonempty draft/lesson history. Deployment prechecks accept exact reviewed journal prefixes of 27/28/29 migrations with 51/54/56 application tables respectively; postchecks require the full 29-entry chain. These local changes authorize no hosted migration.

## Phase 3 — publication and authorized viewing

- Publication is explicit and refers to the latest saved draft ID and revision. Only ACTIVE School Admins may publish. The existing School write lock serializes draft/configuration/publication changes; actor and academic lifecycle are rechecked within the transaction. CLOSED Periods and CLOSED/ARCHIVED years cannot receive publications. The Period must remain within its existing Year and match the saved draft dates/curriculum.
- A publication is a complete immutable event for a Class. It snapshots lesson identities, weekday/clock times, Subject/Teacher/room names and identifiers, Class/Year/Period labels and School timezone. Subsequent configuration, label or assignment changes cannot rewrite published meaning. Earlier draft rows and publication events are retained, including actor, publication timestamp and atomic audit event.
- The effective start is an explicitly selected School-local calendar date within the Period, today or later. Replacements append in strictly increasing effective-date order per Class; same-date replacement, backdating and insertion before a scheduled replacement are rejected. This bounded V1 rule prevents retroactive rewriting. The latest sequence is required, so competing publications cannot silently overwrite one another. Request key/hash replay is idempotent, without automatic retries after ambiguous outcomes.
- A publication repeats weekly through the inclusive snapshotted Period end, or through the day before its replacement starts, whichever comes first. Context-end gaps remain gaps; there is no implicit extension beyond the academic context. Applicability is derived, never written back to historical events. As-of views show the weekly plan applicable on the selected date; they are not calendar-exception or per-day attendance views.
- The first publication requires a nonempty valid draft. A later saved empty draft may explicitly replace it, with a warning and confirmation, to end all earlier lessons from the effective date. It revalidates active curriculum, active Teacher/profile/assignment and optional active same-School room for every remaining occurrence through Period end. Incomplete/excess teaching loads are displayed warnings, not publication blockers. Class/Teacher/room conflicts compare actual half-open clock intervals on shared actual recurring weekdays against published timelines, independently of drafts. Replacing a Class schedule ends its predecessor's applicability; adjacent times and disjoint dates are allowed.
- Admins can view published content by Class or Teacher and inspect preserved publication history, including future replacements. Draft editing never changes a published schedule until explicit publication. Resolving a published conflict may require editing and publishing the indicated Class's replacement first.
- Teachers receive only lessons whose exact published TeacherAssignment still belongs to their ACTIVE same-School Teacher profile, is ACTIVE, matches Class/Subject/Year and covers the selected date. Ended assignments revoke read scope but do not erase published history. No client-supplied Teacher or Class identity can broaden this self-only view. ADR-009 remains the sole academic scope authority.
- Parents choose only children linked through ACTIVE same-School Parent/ParentStudent records and ACTIVE Students. Dated StudentEnrollment resolves the Class/Year for the selected date, including bounded historical enrollments after transfers. An ambiguous placement fails closed. An ended relationship revokes access. The API never falls back to another child's schedule when a selected child has no applicable enrollment/publication.
- Central `timetable.read` is available to School Admin, Teacher and Parent roles; `timetable.manage` remains School Admin only. Platform authority alone grants neither. `/api/v1/timetable/published` exposes role-filtered GET and same-Origin Admin POST; all successes/errors are private/no-store. Read DTOs exclude drafts, internal request hashes and publisher account identifiers. Published history is Admin only.
- Forward `0029_timetable-publications` adds one private RLS table, composite draft/context FK, unique Class sequence/date and School request key. It does not modify 0027/0028. Current contracts are 30 migrations, 57 application tables and 2 Auth recovery tables. Exact reviewed pre-migration prefixes 27/28/29/30 map to 51/54/56/57 tables; postchecks require the complete 30-entry chain.
- Recovery includes full publication JSON and audit history, fingerprints and FK ordering. Older 0027/0028 bundles keep their original inventories and require matching source/migration chains. No hosted migration or release is authorized by local implementation.

Auto-generation, substitutions, exam timetables, calendar exceptions and advanced analytics are deferred. Local synthetic browser coverage and real local SQL/concurrency checks do not constitute authenticated STAGING acceptance.
